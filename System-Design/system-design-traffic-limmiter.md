
# Проектирование ограничителя трафика

Ограничитель трафига необходим для управления скоростью передачи данных от клиента или сервиса. Он ограничивает количество запросов, отправляемых за определенный промежуток времени. Если максимальное количество запросов исчермано, то все последующие блокируются.

Преимущества использования ограничителя трафика:

- Предотвращение нехватки ресурсов, вызванной DoS-атаками (Denial of Service - "отказ в обслуживании");
- Экономия бюджета. Ограничение избыточных запросов освобождает часть серверов и выделяет больше ресурсов для высокоприоритетных API. Это очень важно, если мы используем сторонние платные API;
- Предотвращение перегрузки серверов. Для снижения нагрузки на серверы, ограничитель может фильтровать лишние запросы, которые исходят от ботов или недобросовестных пользователей.

## Шаг 1 Понять задачу и определить масштаб решения

Необходимо обзаться с интервьюером, чтобы понять какого рода ограничитель мы будем делать. Ниже приведены ориентировочные вопросы:
- Какой ограничитель будем делать клиентский или серверный?
- Каким образом он будет ограничивать трафик, по IP, ID пользователя или другим свойствам?
- Каков масштаб системы? Она для стартапа или крупной компании с множеством пользователей?
- Будет ли система работать в распределенном окружении?
- Ограничитель должен быть частью приложения или отдельным сервисом?
- Надо ли уведомлять пользователей, чьи запросы блокируются?

Требования:
- Точная фильтрация избыточных запросов.
- Низкая латентность. Ограничитель не должен увеличивать время возвращения HTTP-ответов;
- Минимально возвожное потребление памяти;
- Распределенное ограничение трафика. Он должен быть доступен разным серверам или процессам.
- Обработка исключения.  Когда запрос прользователя блокируется, возвращаем понятное сообщение об ошибке;
- Высокая отказоустойчивость. Есди возникнут проблемы с ограничителем, это не должно влиять на систему в целом.

## Шаг 2 Предложить общее решение и получить согласие

Существует три варианта реализации:
- Клиентская - не самое надежное место, т.к. клиентские запросы могут быть подделаны, да и типов клиента может быть много.
- Серверная - размещается на сервере, находится под нашим полным контролем;
- В виде промежуточного слоя (приложения), который фильтрует запросы к API и отбрасывает лишние.

Шлюз API - полностью управляемый срвис с поддержкой ограничения трафика, завершения SSL-запросов, аутентификации, ведения белых списков IP-адресов, обслуживания статического содержимого и пр.

Реализация ограничителя на серверной стороне или шлюзе зависит от следующих моментов:
- Текущий технологический стек, а именно язык программирования, кеш, и прочее. Надо убедиться, что все это позволяет реализовать ограничитель на сервере.
- Алгоритм ограничения трафика. Если реализуем на сервере, то алгоритм под нашим контролем, иначе придется довольствоваться тем, что реализовано в готовых решениях (сторонним шлюзом.
- Если уже используем микросервисы и архитектура предусматривает шлюз API, то ограничитель можео добавить в шлюз.
- Разработка своего решения занимает время. Если уресурсов нет, то лучше выбрать готовое коммерческое решение в виде шлюза.

### Алгоритмы ограничения трафика

Существуют следующие алгоритмы ограничения трафика:
- алгоритм маркерной корзины (token bucket);
- алгоритм дырявого ведра (leaking bucket);
- счетчки фиксированных интервалов (fixed window counter);
- журнал скользящих интервалов (sliding window log);
- счетчик скользящих интервалов (sliding window counter).
