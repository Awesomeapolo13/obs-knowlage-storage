
# Системный дизайн

## Масштабирование

Разделение серверов на веб-сервер (где крутится бекенд и фронтенд) и на сервер БД позволяет масштабировать эти компоненты независимо друг от друга.

При выборе типа БД стоит обратить внимание на особенности NoSQL решений:
- приложение нуждается в крайне низкой латентности;
- данные не имеют никаких реляционных связей или не структурированы;
- необходимо только сериализовывать и десериализовывать данные;
- нужно хранить огромные объемы данных.

Вертикальное масштабирование (наращивание) - процесс повышения мощности серверов (процессоров, памяти и прочего).
Горизонтальное масштабирование (расширение) - заключается в добавлении новых серверов в пул ресурсов.

Вертикальное масштабирование подходит для задач с небольшим трафиком. Преимущество - простота. Ограничения:
- Вертикальное масштабирование имеет жесткий лимит. Ресурсы отдельно взятого сервера нельзя увеличивать бесконечно.
- Не предусматривает отказоустойчивости и резервирования избыточных ресурсов. Если один из серверов выйдет из строя, то приложение будет полностью недоступно.

Для крупномасштабных проектов подходит горизонтальное масштабирование.

Чтобы сервер не отвалился при большом количестве запросов лучше всего подключить к нему балансировщик нагрузки.

### Балансировщик

**Балансировщик нагрузки** - ПО, которое равномерно распределяет входящий трафик между веб-серверами, которые указаны у него в списке. Пользователи подключаются к балансировщику по внешнему IP. Сами же сервера используют для взаимодействия внутренние IP. Таким образом пользователи не имеют прямого доступа к серверам.

При наличии нескольких серверов, балансировщик будет равномерно распределять нагрузку между ними. Так же несколько серверов повысят отказоустойчивость системы, т.к. при выходе из строя одного, другие возьмут на себя его нагрузку.

### Репликация

Для повышения отказоустойчивости так же можно использовать **репликацию** для уровня БД. Большинство СУБД поддерживают репликацию типа ведущий-ведомый, где оригинал БД является ведущим узлом, а реплики - ведомыми. Ведущей БД доступны операции редактирования и создания новых записей, ведомые же поддерживают только чтение. В большинстве случаев чтение происходит гораздо чаще, чем запись, поэтому ведомых узлов больше чем ведущих.
Преимущества репликации:
- Повышение производительности за счет распределения операций чтения между репликами;
- Надежность. При разрушении одного из серверов, у нас остаются данные на репликах (мы не потеряем их безвозвратно);
- Высокая доступность. При отказе одного из серверов, остальные продожают работать.

### Кеш

Для улучшения времени загрузки/ответа необходимо использовать **КЕШ** и разместить статические ресурсы (JS/CSS/изображения/видео) в **сети доставки содержимого** (content delivery network, CDN).

**Кеш** - участок памяти, в который временно записываются результаты ресурсоемких ответов или данных, к которым часто обращаются. Это позволяет ускорить обслуживание последующих запросов.

**Уровень кеша** - слой временного хранилища данных, который по своей скорости работы намного опережает БД.
Преимущества отдельного уровня кеша:
- улучшение производительности системы;
- возможность снизить нагрузку на основную БД;
- масштабирование этого уровня независимо от других.

Есть множество стратегий кеширования, например, **кеш сквозного чтения**:
- веб-сервер отправляет запрос к кешу;
- если там есть данные то возвращаем их пользователю;
- если данных нет то веб сервер идет в БД и получает их отттуда;
- полученные данные сохраняются в кеш и отдаются пользователю.

Советы по использованию систем кеширования:
- Определиться с тем когда используем кеш. Лучше использовать при частых операциях чтения и редких операциях изменения. Не забывать что данные должны переноситься в постоянное хранилище, т.к. кеш - энергозависимая память;
- Подобрать время жизни кеша. Слишком маленькое время заставит нас часто  обращаться к БД. Слишком большое время приведет к неактуальности данных;
- Согласованность. Т.е. синхронизированность данных в кеше и БД. Несогласованность может возникнуть, если операции изменения данных в хранилище и кеше выполняются не за одну транзакцию. При масштабировании системы в пределах нескольких регионов может быть непросто поддерживать согласованность.
- Предотвращение сбоев. Наличие одного сервера кеша может стать потенциальной единой точкой отказа (single point of failure, SPOF), это компонент выход из строя которого приводит к отказу всей системы. В связи с этим, чтобы избежать SPOF, лучше иметь несколько серверов кеширования в разных ЦОДах. А так же выделить какой-нибудь дополнительный объекм памяти, который создаст буфер на случай, если память начнет использовать активнее;
- Политика вытеснения. При заполнении кеша до отказа, каждая новая запись в нем удаляет существующую. Это вытеснение кеша. Самой распространенной политикой считается вытеснение давно не используемых данных (least-recently-used, LRU). Так же есть вытеснение наименее часто используемых данных (least-frequently-used, LFU) или метод FIFO.

**CDN** - сеть географически распределенных серверов, которая используется для доставки статического содержимого. Эти сервисы кешируют изображения, видео, CSS, JavaScript и прочие. Так же CDN может использоваться и для кеширования динамического содержания, но тут не об этом.

Общий принцип работы CDN: когда пользователь посещает веб-сайт, бижайший к нему CDN сервер доставляет статическое содержимое. Чем ближе географически сервер CDN к клиенту, тем быстрее загружается статическое содержимое.

Более детальный принцип работы CDN:
1) Пользователь пытается получить изображение с помощью URL-адреса, например https://mysite.cloudfront.net/logo.jpg
2) Если в кеше CDN изображения нет, он запрашивает файл из оригинального источника (некоего веб-сервера или облачного хранилища).
3) Источник возвращает CDN файл вместе с заголовком TTL, который определяет как долго оно будет находиться в кеше.
4) CDN кеширует изображение и возвращает его пользователю. В кеше оно хранится до окончания времени жизни.
5) Теперь когда другой пользователь попытается получить то же самое изображение CDN вернет его сразу из кеша (если его время жизни еще не истекло).

Нюансы использования:
- Стоимость. CDN предоставляются сторонними компаниями, а перемещение данных между разными CDN ресурсоемкая (в том числе в денежном эквиваленте) задача. Так же, нет смысла кешировать редко используемые ресурсы.
- Выбор времени жизни кеша. Срок должен быть не слишком длинным (потеря актуальности) или коротким (частые перезапросы с основного источника).
- Возможность сбоев. При недоступности CDN клиент должен уметь обнаружить это и запросить ресурсы напрямую из источника.
- Аннулирование файлов. Файлы можно удалять из CDN до истечения их сроков годности через:
	- аннулирование объекта CDN с помощью API, предоставляемых поставщиками;
	- использование версионирования, чтобы возвращать разные версии объектов. Например, через URL типа image.png?v=2.

При добавления CDN и кеширования мы снижаем нагрузку на БД и улучшаем производительность, т.к. статические файлы больше не раздаются серверами.

### Веб уровень без сохранения состояния

Для горизонтального масштабирования веб-уровня необходимо вынести из него состояние, а именно информацию о пользовательских сеансах (или иное). Данные сеансов лучше записывать в постоянные хранилища, которые будут источниками этого состояния для веб-уровня.

При использовании архитектуры веб-уровня с сохранением состояния, нам необходимо отправлят запросы на те сервера, на которых прошла аутентификация, т.к. они помнят информацию о пользователе. Такой подход ведет к накладным расходам при добавлении и удалении серверов, а так же при выходи их из строя.

Чтобы сделать систему независимой от состояния, нужно вынести информацию о пользователе в отдельное хранилище, чтобы Веб-уровень мог обращаться за ней в любое время. Это позволит серверам на веб-уровне автомасштабироваться, т.е. добавление и удаление веб-серверов происходит автоматически в зависимости от объемов трафика.

### Центры обработки данных

В нормальных условиях пользователи направляются в ближайший ЦОД с помощью geoDNS. GeoDNS - это сервси, который сопоставляет доменные имена с IP-адресами в зависимости от местонахождения пользователя.

Копия приложения находится на разных ЦОД, хранилище состояния вынесено за из переделы. Если один из ЦОД отвалится, то весь трафик идет в оставшиеся.

Для реализации архитетуры с несколькими ЦОД необходимо решить несколько технических вопросов;
- Перенаправление трафика. Выбрать инструмент, который направить трафик к ближайшему ЦОД (например, GeoDNS).
- Синхронизация данных. Пользователи могут работать с разными локальными БД и кешами в зависимости отрегиона. В случае сбоя трафик может быть перенаправлен к ЦОД, в котором нет запрашиваемых данных. Распространенное решение - репликация данных между ЦОДами.
- Тесты и развертывание. В конфигурации разных ЦОД, тестирование приложения нужно проводить в разных местах. Так же необходимы автоматические средства развертывания, в частности для поддержания согласованности всех ЦОД.

Для улучшения масштабируемости так же необходимо разделить компоненты системы, чтобы масштабировать их независимо друг от друга. Для этого часто используют очереди сообщений.

### Очереди сообщений

Очереди сообщений - компонент, который поддерживает асинхронное взаимодействие. По сути это буфер, который распределяет асинхронные запросы. Сервисы ввода (издатели) создают сообщение и публикуют его в очереди, а другие сервисы (потребители) подключаются к очереди, забирают сообщения и обрабатывают их. 

Производитель может публиковать сообщения, даже если потребитель не в состоянии их обработать. И наоборот, потребитель может считывать сообщения назависимо от работоспосообности издателя.

В зависимости от количества сообщений в очереди можно регулировать количетсво потребителей или издателей независимо друг от друга.

### Логирование, метрики, автоматизация

**Логироание**. Мониторинг логов это важная вещь. Логи можно отслеживать на каждом отдельном сервере, но существуют инструменты, которые позволяют собирать логи в централизированном сервисе.

**Метрики**. Сбор разных метрик позволяет лучше понять предметную область и оценить работоспособность системы. Могут пригодиться следующие метрики:
- метрики уровня сервера: процессор, память, дисковый вводы/вывод и пр.;
- агрегируванные метрики: производительность всего уровня БД, уровня кеша и пр.
- ключевые бизнес-метрики: суточное еоличество активных пользователей, удержание, доход.

**Автоматизация**. Рекомендуется применять непрерывную интеграцию - когда каждая фиксация кода автоматически проверяется, что помогает обнаружить проблемы на ранних этапах. Кроме того, автоматизация процессов сборки, тестировани, развертывания и пр. может существенно повысить продуктивность самих разработчиков.

### Масштабирование БД

Как и в случае с любым масштабированием для БД есть две стратегии: вертикальное и горизонтальное масштабирование.

Вертикальное масштабирование - повышение производительности на счет добавления ресурсов процессора, памяти и диска. Серверы БД довольно мощные.  Есть серьезные ограничения:
- есть аппаратные ограничения, рано или поздно понадобится новый сервер;
- высокий риск возникновения единой точки отказа;
- такое масштабирование имеет высокую общую стоимость (мощные серверы очень дорогие).

Горизонтальное масштабирование  - добавление новых серверов.
Шардинг позволяет разделить крупные объемы данных на более мелкие и простые части (шарды). Шарды имеют одну и ту же схему, но каждый хранит уникальные данные.

![[Pasted image 20260407125553.png]]

На рисунке выше видно, как сервер БД для сохранения пользовательской информации выбирается на основе ID пользователя. При каждом обращении к данным используется функция хеширования, которая находит подходящий шард. В примере функция хеширования имеет вид `user_id % 4`. Если результат равен 0, то выбирается сегмент 0, то же актуально и для остальных шардов.

При шардировании очень важно выбрать стратегию для построения ключа. Ключ шардинга (или ключ раздела) состоит из одного или нескольких столбцов, на основе которых происходит распределение данных. Важно чтобы двнные на основе ключа распределялись равномерно.

Шардинг так же создает и дополнительные трудности:
- Повторное сегментирование данных. Может понадобиться либо когда отдельный шард полностью заполняется из-за стремительного развития системы, либо когда  некоторые шарды заполняются быстрее других из-за неравномерного распределения данных. Тогда необходимо обновить функцию сегментирования и переместить имеющиеся данные. Для решения этой проблемы часто применяют согласованное хеширование.
- Проблема знаменитостей. Слишком частое образение к определенному шарду может вывести из строя все приложение. Представим что информация о Кетти Перри, Бибере и Леди Гаге оказалась в одном шарде. Для решения проблемы, вероятно, придется выделить по отдельному шарду на каждую знаменитость.
- Соединение и денормализация. После сегментирования БД между несколькими серверами становится сложно выполнять операции соединения, охватывающие несколько шардов. распространенное решение - денормализация БД таким образом, чтобы запросы могли выполняться в рамках одной таблицы.

### Миллионы пользователей

Масштабирование процесс пошаговый. Перечисленные выше методики могут здорово помочь. Но если аудитория перевалит за несколько миллионов этого может не хватить. Придется внедрять более тонкие оптимизации и новые стратегии. Возможно вообще разбить всю систему на множество микросервисов.

Для масштабирования системы, которая поддерживает миллионы пользователей необходимо следовать следующим шагам:
- веб-уровень не должен хранить состояния;
- резервирование должно быть предусмотрено на каждом уровне;
- кеширование надо проводить как можно более активно;
- система должна поддерживать более одного ЦОДа;
- статические ресурсы надо хранить в CDN;
- для масштабирования данных следует применять щардинг;
- уровни должны быть разделены на отдельные сервисы;
- необходимо выполнять мониторинг системы и использовать средства автоматизации.
