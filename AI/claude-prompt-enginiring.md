
# Промпт инжиниринг

## Компоненты промпта

1) Контекст задачи. Указать зачем мы все это делаем , как связано с остальной системой.

```shell
У нас есть пользователи с авторизацией. Хотим дать пользователю возможность управлять своими категориями трат.
```

Контекст важен потому, что часть архитектурных решений зависит от него. Без контекста Claude может, например, сделать категории глобальными, а не привязанными к пользователю.

2) Задача. Что конкретно нужно сделать или поменять. Чем детальнее описаны поля сущностей и методы, тем точнее результат. Клод и сам это все может придумать, но не факт что это совпадет с нашими пожеланиями.


```shell
Создать модуль категорий: контроллер, сервис, репозиторий, сущность.
```

3) Детали реализации. Конкретные технические требования: поля, типы, паттерны.

```shell
Поля Category: id (uuid), name (string), color (hex string), icon (string), userId (FK). Методы: findAllByUser(userId), create(dto, userId), update(id, dto), remove(id, userId).
```

4) Ожидаемый результат. Что должно работать. 

```shell
POST /categories создаёт категорию, привязанную к текущему пользователю.
GET /categories возвращает только категории авторизованного пользователя.
```

5) Ограничения. Они описывают, что делать не нужно. Без них Клод может неожиданно переписать существующий код или добавить лишние зависимости.

```shell
Не трогай существующий AuthModule. Используй тот же паттерн, что и в AuthModule. Не добавляй новые зависимости — только те, что уже установлены. Не меняй схему БД, только добавь новую таблицу.
```

## Компоненты промпта об ошибке

1) Копировать ошибку целиком, без сокращений. Не писать "возникла какая-то ошибка", необходим более точный текст, это ускорит решение задачи.

```shell
TypeError: Cannot read properties of undefined (reading 'userId') at TransactionService.findAll (transaction.service.ts:23:45)
```

2) Контекст воспроизведения. Описать когда и при каких условиях ошибка воспроизводится. Это сузит поиск с, например, "всех мест где используется userId", до  конкретного эндпоинта и сценария.

```shell
Ошибка появляется при GET /transactions когда пользователь не авторизован. С валидным JWT работает нормально.
```

3) Ожидание vs факт. Описать какое поведение ожидалось от кода вместо ошибки.

```shell
Ожидал: 401 Unauthorized (пользователь не авторизован) Получил: 500 Internal Server Error
```

4) Если ошибка касается пронтенда, то можно передать скриншот через вставку Ctrl + V.

Ошибки лучше исправлять в той же сессии, где был написан код, т.к. весь контекст уже есть. Если не помогло:

```shell
Исправление не сработало, теперь ошибка:
[новая ошибка]
```

После этого Клод продолжит итерацию:
1) Описали ошибку → Claude исправил CORS
2) Новая ошибка → Claude скорректировал DTO-валидацию
3) Слдующая ошибка → Claude исправил отправку данных с фронтенда
