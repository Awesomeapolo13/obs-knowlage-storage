## Предлагаемая структура на Purple School

1. **CMD**: Это папка для точки входа приложения. Содержит `main`-файлы, которые запускают приложение. Если у вас несколько приложений, например, веб-сайт и API, для каждого будет отдельный файл в этой папке.
2. **Internal**: Здесь содержатся основные бизнес-модули, которые не экспортируются наружу и не могут быть использованы как внешняя зависимость. Они распределяются на отдельные модули по функциональности (например, пользователи, статистика).
3. **Package (pkg)**: В этой папке размещается общий код библиотек, который может переиспользоваться в других проектах, такие как обработчики, подключения к базам данных и другие утилиты.
4. **Configs**: Шаблоны и модули конфигурации приложения. Здесь настроены параметры подключения к базам данных, URL и другие конфигурации.
5. **Migrations**: Хранит миграции базы данных. Только важно учитывать, что структура может расширяться и дополняться в зависимости от потребностей проекта.

Основное внимание необходимо уделить правильному распределению модулей и зависимостей внутри `internal`, чтобы обеспечить гибкость и легкость в поддержке.

Чтобы поделить модули приложения (в директории internal) на слои можно использовать следующую структуру:
1. **Слой обработчика (Handler Layer)**: Обрабатывает запросы, управляет извлечением параметров и преобразованием данных, например, из JSON. Иногда часть бизнес-логики может размещаться здесь, чтобы избежать избыточного кода в отдельном сервисном слое.
2. **Сервисный слой (Service Layer)**: Основное место для бизнес-логики. В важных случаях логика может быть перенесена сюда.
3. **Payload (или DTO - Data Transfer Object)**: Структуры данных для передачи информации, как входящей, так и исходящей из системы, например, данные логина (e-mail и пароль).
4. **Репозиторий (Repository)**: Управляет доступом к базе данных, предоставляя ограниченные методы для работы с данными. Разделяет взаимодействие между приложением и базой данных, например, пользовательский, линк и статистический репозитории отдельно.
5. **Ошибки**: Список часто используемых ошибок, например, для тестирования.
Взаимодействие происходит следующим образом: хендлер принимает и отправляет payload, может взаимодействовать с сервисом, который обращается к репозиторию. Иногда хендлер направляется прямо к репозиторию.
